# Debugging: CSS, Stacking Contexts, & SSR Hydration

## Why It Matters
Visual and rendering bugs—such as modal overlays appearing behind headers, layouts breaking on mobile viewports, or server-side hydration mismatches—directly impact brand credibility and user conversions. Senior frontend engineers must diagnose and resolve layout bugs by inspecting stacking contexts, debugging mobile overflows, and correcting markup mismatches in Server-Side Rendered (SSR) frameworks.

---

## Core Concepts & Mental Models

### 1. The z-index & Stacking Context Pitfalls
A common visual bug is an element with `z-index: 9999` rendering *behind* an element with `z-index: 1`. 
*   **The Stacking Context**: The browser parses z-index rules only within the active Stacking Context. A Stacking Context is created by:
    - Elements with `position: relative` or `absolute` paired with a non-static `z-index`.
    - Elements with `position: fixed` or `sticky`.
    - Flexbox or Grid children with a non-static `z-index`.
    - Elements with an `opacity` less than `1`.
    - Elements using `transform`, `filter`, or `will-change` properties.
*   **The Trap**: If Element A (inside Stacking Context 1) has `z-index: 9999`, and Stacking Context 1 itself is ranked below Stacking Context 2 in the DOM hierarchy, Element A will render behind any element in Stacking Context 2, regardless of how high its z-index is.

### 2. Layout Breaking on Mobile (Horizontal Scroll Bug)
Mobile screens are narrow. A horizontal scrollbar appearing unexpectedly is the number one mobile layout bug:
*   **The Cause**: Elements expanding beyond the viewport width, often due to:
    - Fixed pixel widths (e.g. `width: 600px`) on elements inside responsive containers.
    - Negative margins pushing cards outside container margins.
    - Long strings of text (like URLs) that do not wrap.
*   **The Debugging Path**: Open the mobile device emulator in Chrome DevTools. Run this script in the console to locate the specific element that is wider than the document body:
    ```javascript
    document.querySelectorAll('*').forEach(el => {
      if (el.offsetWidth > document.body.offsetWidth) {
        console.log('Overflowing Element:', el);
      }
    });
    ```

### 3. Server-Side Rendering (SSR) Hydration Mismatch
In SSR frameworks (like Next.js), the server compiles the HTML body, sends it, and the browser displays it. Then, JavaScript loads and **hydrates** the static HTML, linking React event listeners to DOM elements.
*   **The Hydration Mismatch**: If the initial HTML compiled on the server does not *exactly* match the virtual DOM tree generated by the client during the first render, React logs warnings (e.g. `Text content did not match. Server: "X" Client: "Y"`).
*   **Common Causes**:
    - Querying client-only global variables (like `window` or `localStorage`) directly during rendering.
    - Using dynamic data generators (like `Date.now()` or `Math.random()`) during rendering.
    - Invalid HTML markup (e.g. nesting a `<div>` inside a `<p>` tag, which the browser automatically corrects in the DOM, creating a mismatch).

## Real-World Case Study / Examples

### Debugging a Next.js Hydration Mismatch
A header component displays either "Welcome back, Bob" (if logged in) or "Log in" by checking `localStorage` for a session token on load.

**Broken Code**:
```javascript
function Header() {
  const token = typeof window !== "undefined" ? localStorage.getItem("token") : null;
  return <div>{token ? "Welcome back, Bob" : "Log in"}</div>;
}
```
**The Bug**: During server render, `window` is undefined, so the server outputs "Log in." On the client, `window` exists and `token` is found, so React client-side attempts to render "Welcome back, Bob." The mismatch triggers a console warning and can cause rendering glitches.

**The Fix**: Defer token rendering using a `useEffect` hook to ensure the initial client render matches the server output:
```javascript
function Header() {
  const [isClient, setIsClient] = useState(false);
  useEffect(() => {
    setIsClient(true);
  }, []);

  const token = (isClient && typeof window !== "undefined") ? localStorage.getItem("token") : null;
  return <div>{token ? "Welcome back, Bob" : "Log in"}</div>;
}
```

## Common Interview Traps

### The "z-index = 999999" Quick Fix
*   **The Trap**: Suggesting setting a higher z-index to resolve overlay issues during design reviews.
*   **The Answer**: Explain that changing z-index values arbitrarily leads to "z-index wars" and fails if the elements belong to different stacking contexts. Solve it by:
    1.  Flattening the DOM tree.
    2.  Promoting the overlay node to the document body root using **React Portals** to create a clean stacking context.

---

## Junior vs. Senior View

*   **Junior View**: "Fix z-index issues by setting it to a huge number. Fix mobile overflow by adding `overflow-x: hidden` to the body. Mute hydration warnings by using `suppressHydrationWarning`."
*   **Senior View**: "Resolve visual overlaps by tracking and managing stacking contexts (using portals for overlays). Prevent mobile layout issues by using responsive box designs, and eliminate SSR mismatches by ensuring initial renders match server outputs and correcting HTML semantics."

## Dropdown closing unexpectedly & z-index issue
- **Dropdown closing unexpectedly**: Caused by focus loss or click handlers trigger bubbles closing active overlays. Prevent by stopping event propagation.
- **z-index issues**: Triggered by parent stacking contexts clipping child overlays. Resolve by using Portals.
