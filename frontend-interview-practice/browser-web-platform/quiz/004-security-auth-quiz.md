# Quiz: CORS, CSP, XSS, CSRF, & JWTs

## Questions

### Question 1 (Medium - CORS Preflight Trigger)
Which of the following fetch requests will trigger a CORS preflight (`OPTIONS`) request?
- **Request A**:
  ```javascript
  fetch("https://api.example.com/data", {
    method: "GET",
    headers: { "Content-Type": "text/plain" }
  });
  ```
- **Request B**:
  ```javascript
  fetch("https://api.example.com/data", {
    method: "POST",
    headers: { "Content-Type": "application/json" }
  });
  ```
- **Request C**:
  ```javascript
  fetch("https://api.example.com/data", {
    method: "POST",
    headers: { "X-Custom-Header": "value" }
  });
  ```

### Question 2 (Hard - CSRF sameSite Leak)
If a session cookie is configured with `SameSite=Lax`, which of the following actions executed on a malicious third-party site `evil.com` will successfully trigger a request containing the session cookie to `bank.com`?
- **Action 1**: An `<img>` tag requesting `bank.com/logo.png`.
- **Action 2**: A `<form>` post request to `bank.com/transfer`.
- **Action 3**: A user clicking a link `<a href="https://bank.com/dashboard">Dashboard</a>`.
- **Action 4**: A `fetch()` request to `bank.com/api/balance`.

### Question 3 (Senior - CSP Nonce Injection Bypass)
Consider this CSP configuration. Does it protect the site against XSS if an attacker can inject arbitrary text into the page body? What is a nonce, and how can an attacker bypass it if the nonce is static across pages?
```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-xyz123';
```

## Answer Key & Explanations

### Question 1: CORS Simple Request Rules
- **Difficulty:** Medium
- **Answer:** **Request B** and **Request C** will trigger preflight requests; **Request A** will skip it.
- **Explanation:**
  - A browser skips the preflight request (marks it as a "Simple Request") if it satisfies all these conditions:
    1. The HTTP method is `GET`, `HEAD`, or `POST`.
    2. Only standard headers are set (like `Accept`, `Accept-Language`, `Content-Language`, `Content-Type`).
    3. The `Content-Type` is limited to: `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain`.
  - **Request A** uses `GET` and `text/plain`, so it is a simple request and skips preflight.
  - **Request B** uses `application/json` as the `Content-Type`. Since JSON is not in the allowed list of simple types, it triggers a preflight request.
  - **Request C** sets a custom header `X-Custom-Header`, which triggers a preflight request immediately.
- **Common Mistakes:** Thinking all `POST` requests require preflight, or that JSON is a simple content-type.
- **Senior-Level Insight:** Minimize custom headers and keep content-types simple in performance-sensitive public APIs to avoid the latency cost of preflight OPTIONS requests.

---

### Question 2: SameSite=Lax Cookie Transmission Limits
- **Difficulty:** Hard
- **Answer:** Only **Action 3** will transmit the cookie; Actions 1, 2, and 4 will block it.
- **Explanation:**
  - `SameSite=Lax` cookies are designed to protect against CSRF while maintaining user-friendly links.
  - The browser will only append `SameSite=Lax` cookies if:
    1. The request method is "safe" (read-only, i.e., `GET`, not `POST`).
    2. The navigation is top-level (changes the URL address bar of the browser).
  - **Action 1** (image src) is a subrequest, not a top-level navigation, so the cookie is blocked.
  - **Action 2** (form POST) uses an unsafe method `POST`, so the cookie is blocked.
  - **Action 3** (anchor link GET) is a top-level safe navigation, so the cookie is successfully sent.
  - **Action 4** (fetch API) is a subrequest within the page, so the cookie is blocked.
- **Common Mistakes:** Believing `SameSite=Lax` cookies are blocked on all third-party interactions or sent on all GET requests (like images).
- **Senior-Level Insight:** While `SameSite=Lax` provides strong protection against CSRF, always combine it with anti-CSRF tokens or custom headers for state-modifying requests (POST/PUT/DELETE).

### Question 3: CSP Nonce Security and Static Tokens
- **Difficulty:** Senior
- **Answer:** Yes, it protects against XSS if the nonce is cryptographically secure and changes on every single request. However, if the nonce is static, it fails completely.
- **Explanation:**
  - A **nonce** (number used once) is a unique, cryptographically secure token generated by the server on each request and injected into the CSP header and allowed `<script nonce="TOKEN">` tags.
  - If an attacker attempts to inject a script `<script>malicious()</script>`, it will fail to execute because it lacks the correct nonce token matching the header.
  - If the nonce is **static** (e.g. always `xyz123`), the attacker can simply hardcode the nonce in their payload: `<script nonce="xyz123">malicious()</script>`, completely bypassing the CSP protection.
- **Fix:** The server must generate a unique, cryptographically secure random token (e.g., UUID/crypto random bytes) on **every HTTP request**, ensuring it cannot be guessed or reused.
- **Common Mistakes:** Hardcoding nonces in static HTML files or stylesheets.
- **Senior-Level Insight:** CSP nonces require a dynamic server environment. If your site is statically generated (SSG) and served from a CDN, use hash-based CSP configurations (`sha256-...`) to verify script signatures instead.

---

### Question 4 (JWT Handling Security)
Explain where access tokens and refresh tokens should be stored to prevent CSRF and XSS attacks.
**Answer:** Access tokens should be stored in memory (React state). Refresh tokens should be stored in an HttpOnly, Secure, SameSite cookie, protecting them from XSS reads.
